# 抢杠（Chankan）State Fix 业务逻辑深度分析

## 1. 现象

日志中出现：
```
ChanKan State Fix: Reverted Player 3's MinKan of tile 12 to Pon
ChanKan State Fix: Reverted Player 2's MinKan of tile 24 to Pon
```

## 2. 血战到底规则下的抢杠

### 2.1 规则定义（rules.md §11）

- **抢杠（Chankan）**：+1番  
- **条件**：在别人**加杠（补杠）**时，抢杠和牌（荣和）  
- **含义**：别人加杠打出的那张牌，正好是你听的牌，你可以用这张牌和牌。

### 2.2 物理结果

- **加杠者**：本来要做的是「碰 → 加杠」（3 张 → 4 张明杠）。  
  一旦被抢杠，那张「加杠的牌」被和牌者拿走，所以加杠**不成立**。  
- **结果**：加杠者手上只应保留**碰**（3 张），第 4 张牌归和牌者。  
- **和牌者**：用这张牌荣和，牌型里包含这张「抢」来的牌。

因此，从牌面事实和计分角度：  
**被抢杠的一方 = 只有碰，没有杠。**

## 3. 代码里的事件顺序

### 3.1 事件流

1. **Kakan 事件**  
   - 加杠者（例如 Player 3）声明加杠，事件带着 `actor=3`、加杠的牌等下发。  
   - 在 `update.rs::kakan()` 里，**先**对加杠者本人做状态更新：  
     - `pons.retain(|&t| t != pai)`（从碰里去掉这张）  
     - `minkans.push(pai)`（加入明杠）  
   - 此时加杠者的状态已经是 **MinKan（4 张）**。  
   - 同时，其他家若听这张牌且满足定缺等，会设置 `chankan_chance`、`chankan_kakan_actor`、`chankan_kakan_tile`。

2. **Hora 事件（抢杠和）**  
   - 某玩家选择 Ron（抢杠），进入 `board.rs::handle_hora()`。  
   - 此时加杠者的状态**仍然是** MinKan（因为 Kakan 已经应用过了）。  
   - 但物理上这张牌已被和牌者拿走，加杠者实际只有碰。

### 3.2 为何需要「State Fix」

- 事件是**顺序应用**的：Kakan 一应用就把加杠者改成 MinKan，**当时**还不知道会不会被抢杠。  
- 只有在处理 Hora 时才能确定这是抢杠，并知道「加杠不成立」。  
- 因此必须在 **handle_hora** 里做一次**状态回滚**：把被抢杠者的 MinKan 改回 Pon，使内存状态与真实牌面一致。

否则会出现：

- 加杠者状态里仍是 4 张（明杠），但实际第 4 张已被和牌者拿走 → **多出一张“幽灵牌”**。  
- 根（gen）等计算、后续 replay/校验都会错。

## 4. State Fix 在做什么（board.rs）

在 `handle_hora` 里，当判定为抢杠（`is_chankan`）时：

1. **刮风退款**  
   - 加杠时的即时支付（刮风）作废，按规则退给当时付过钱的玩家。  
   - `last_kan_revenue` 清零，对应杠记录置为无效。

2. **状态回滚（ChanKan State Fix）**  
   - 从**和牌者**的 `chankan_kakan_tile` 取得「被抢的那张牌」。  
   - 在**被抢杠者**（kan_actor）的 `minkans` 里找到这张牌，从明杠中移除。  
   - 把这张牌再加回该玩家的 `pons`（恢复为碰）。  
   - 更新该玩家的 shanten/waits 等缓存。

这样，被抢杠者的状态就变成：**只有碰（3 张），没有杠**，与规则和物理牌面一致。

## 5. 结论：在血战到底中是否正确

**结论：正确。**

| 维度           | 说明 |
|----------------|------|
| **规则符合**   | 血战到底中抢杠 = 加杠不成立，被抢杠者只保留碰，第 4 张归和牌者。代码把 MinKan 回滚为 Pon，与规则一致。 |
| **计分/根**    | 抢杠时被抢杠者的根不计算（加杠的牌被抢走），已在 agari 计算中通过 `exclude_gen_tile` 等处理；状态回滚保证「杠数」「副露」等与计分逻辑一致。 |
| **事件顺序**   | 先应用 Kakan（状态变为 MinKan），再在 Hora 时发现是抢杠并回滚，是当前事件模型的合理实现方式。 |
| **日志含义**   | `ChanKan State Fix: Reverted Player X's MinKan of tile Y to Pon` 表示：检测到抢杠，已把玩家 X 的「明杠 Y」改回「碰 Y」。这是**预期行为**，不是异常。 |

## 6. 为何会看到这条 INFO 日志

- 每次**发生抢杠**且成功找到对应 MinKan 并回滚时，都会打这条 INFO。  
- 你的对局里 Player 2、Player 3 分别被抢杠过一次，因此各出现一次 Revert 日志。  
- 若希望减少日志噪音，可以改为 `log::debug!`；**不建议**删除或跳过回滚逻辑本身。

## 7. 小结

- **业务逻辑**：抢杠时把被抢杠者的 MinKan 回滚为 Pon，在血战到底规则下是**正确**的。  
- **实现方式**：在 Hora 处理中做一次状态修正，与「先应用 Kakan、后判定抢杠」的事件顺序匹配。  
- **日志**：INFO 仅表示发生了抢杠并完成了状态回滚，属正常情况。
