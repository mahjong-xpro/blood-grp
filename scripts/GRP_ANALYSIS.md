# GRP 在血战到底麻将中的实现有效性分析

## 执行摘要

本文档深度分析当前 GRP 实现在血战到底麻将中的有效性，识别潜在问题和改进空间。

**总体评估**：当前实现**基本有效**，但存在**关键信息缺失**，可能影响预测准确性。

**更新**：已实现**方案A优化**，添加已胡牌玩家信息到GRP特征中（GRP_SIZE从5扩展到9）。

## 1. 当前实现分析

### 1.1 GRP 特征格式

当前 GRP 特征（`libblood/src/dataset/grp.rs`）：

```rust
// 每个局的特征：5 维向量
[kyoku, score[0]/10000, score[1]/10000, score[2]/10000, score[3]/10000]
```

**包含的信息**：
- ✅ 当前局数（kyoku）
- ✅ 各玩家当前分数（归一化）

**缺失的信息**：
- ❌ **哪些玩家已胡牌**（`players_agari`）
- ❌ **定缺状态**（`ding_que`）
- ❌ **流局类型**（查花猪、查大叫）
- ❌ **剩余牌数**（`tiles_left`）

### 1.2 特征提取逻辑

```rust
// libblood/src/dataset/grp.rs:89-150
pub fn load_events(events: &[Event]) -> Result<Self> {
    // 从后往前遍历事件
    for ev in events.iter().rev() {
        match *ev {
            Event::Hora { deltas, .. } | Event::Ryukyoku { deltas, .. } => {
                // 累积最终分数变化
                vec_add_assign(&mut final_deltas, &ds);
            }
            Event::StartKyoku { kyoku, scores, .. } => {
                // 提取特征：只有局数和分数
                kyoku_info.push(kyoku as f64);
                kyoku_info.extend(scores.iter().map(|&score| score as f64 / 10000.));
            }
        }
    }
}
```

**问题**：
1. 只提取 `StartKyoku` 时的分数，**没有提取局中状态**
2. 没有记录哪些玩家已胡牌
3. 没有记录定缺信息

## 2. 血战到底麻将的特殊规则

### 2.1 3人胡牌结束规则

**规则**：当 3 个玩家胡牌后，游戏立即结束，第 4 个玩家无法再胡牌。

**对 GRP 的影响**：
- GRP 需要预测"谁会先胡牌"和"谁会最后无法胡牌"
- 当前特征**没有包含已胡牌玩家信息**，GRP 无法知道：
  - 当前已有几人胡牌
  - 哪些玩家已胡牌
  - 距离游戏结束还有多远

**示例场景**：
```
局 1: 玩家 0 胡牌 → 分数变化
局 2: 玩家 1 胡牌 → 分数变化
局 3: 玩家 2 胡牌 → 游戏结束（玩家 3 无法胡牌）
```

当前 GRP 特征：
```
[1, 2.5, 2.5, 2.5, 2.5]  # 局 1 开始
[2, 2.6, 2.5, 2.5, 2.4]  # 局 2 开始（玩家 0 已胡牌，但特征中没有体现）
[3, 2.6, 2.6, 2.5, 2.3]  # 局 3 开始（玩家 0,1 已胡牌，但特征中没有体现）
```

**问题**：GRP 无法区分：
- 玩家 3 在局 3 时"还有机会胡牌" vs "已无法胡牌"（因为已有 2 人胡牌）

### 2.2 定缺规则

**规则**：每个玩家必须选择一种花色作为"定缺"，不能打出定缺花色，不能以定缺花色胡牌。

**对 GRP 的影响**：
- 定缺会影响玩家的胡牌概率
- 定缺会影响分数变化（如果违反定缺规则会被罚分）
- 当前特征**没有包含定缺信息**

**示例场景**：
```
玩家 0 定缺：万子
玩家 1 定缺：条子
玩家 2 定缺：筒子
玩家 3 定缺：万子
```

如果玩家 0 手牌中还有很多万子，说明：
- 玩家 0 的胡牌概率较低（因为不能打万子）
- 玩家 0 可能成为"花猪"（流局时还有定缺花色）

**问题**：GRP 无法考虑定缺对排名的影响。

### 2.3 流局规则（查花猪、查大叫）

**规则**：
1. **查花猪**：流局时，还有定缺花色牌的玩家向其他玩家赔付 16000 点
2. **查大叫**：流局时，未听牌玩家向听牌玩家赔付

**对 GRP 的影响**：
- 流局会导致**大幅分数变化**（16000 点 = 1.6 个归一化单位）
- 当前特征**没有区分流局类型**
- GRP 可能无法准确预测流局时的排名变化

**示例场景**：
```
局 4: 流局
- 玩家 0: 花猪 → -16000 点
- 玩家 1,2,3: 非花猪 → +5333 点（每人）
- 玩家 1,2: 听牌 → +1500 点（查大叫）
- 玩家 3: 未听牌 → -1500 点（查大叫）
```

最终分数变化可能很大，但 GRP 特征中只有：
```
[4, 2.5, 2.5, 2.5, 2.5]  # 局 4 开始时的分数
# 没有流局类型信息
```

## 3. 潜在问题分析

### 3.1 问题 1：缺少已胡牌玩家信息

**严重程度**：🔴 **高**

**影响**：
- GRP 无法准确预测"3人胡牌结束"的情况
- 在已有 2 人胡牌时，GRP 无法知道"只剩 1 个胡牌机会"
- 可能导致奖励信号不准确

**示例**：
```
场景 A: 已有 2 人胡牌，玩家 3 分数领先
- 实际情况：玩家 3 很可能无法胡牌（只剩 1 个机会）
- GRP 预测：可能高估玩家 3 的排名（因为没有已胡牌信息）
- 结果：奖励信号不准确
```

### 3.2 问题 2：缺少定缺信息

**严重程度**：🟡 **中**

**影响**：
- GRP 无法考虑定缺对胡牌概率的影响
- 无法预测"花猪"情况
- 可能影响排名预测准确性

**缓解因素**：
- 定缺的影响可能通过分数变化间接体现
- 如果玩家违反定缺或成为花猪，分数会大幅下降，GRP 可能能学习到

### 3.3 问题 3：流局时的特殊处理

**严重程度**：🟡 **中**

**影响**：
- 流局时的查花猪、查大叫会导致大幅分数变化
- GRP 可能无法准确预测流局时的排名

**缓解因素**：
- 流局是游戏结束事件，GRP 只需要预测最终排名
- 如果训练数据中有足够的流局样本，GRP 可能能学习到模式

### 3.4 问题 4：特征提取时机

**严重程度**：🟢 **低**

**当前实现**：只在 `StartKyoku` 时提取特征

**潜在问题**：
- 如果一局中有多个玩家胡牌，只记录局开始时的状态
- 可能丢失局中的关键信息

**示例**：
```
局 1 开始: [1, 2.5, 2.5, 2.5, 2.5]
局 1 中: 玩家 0 胡牌 → 分数变化
局 2 开始: [2, 2.6, 2.5, 2.5, 2.4]  # 只记录局 2 开始时的状态
```

**评估**：
- 对于排名预测，局开始时的状态可能已经足够
- 局中的分数变化会在下一局的 `StartKyoku` 中体现

## 4. 有效性评估

### 4.1 当前实现的优势

✅ **简化特征**：5 维特征简单高效，训练速度快

✅ **核心信息**：局数和分数是排名预测的核心信息

✅ **历史信息**：GRU 能够处理序列，学习历史模式

✅ **实际效果**：如果训练数据充足，GRP 可能能学习到：
- 分数领先的玩家更可能获得好排名
- 分数差距越大，排名越稳定
- 3人胡牌结束的模式（通过分数变化间接学习）

### 4.2 当前实现的劣势

❌ **信息缺失**：缺少已胡牌玩家、定缺等关键信息

❌ **预测准确性**：可能无法准确预测"3人胡牌结束"的情况

❌ **奖励信号质量**：可能影响强化学习训练的效果

### 4.3 总体评估

**有效性评分**：**6.5/10**

- **基本有效**：核心功能（排名预测、奖励计算）可以工作
- **有改进空间**：添加关键信息可以显著提升准确性

## 5. 改进建议

### 5.1 高优先级改进

#### 建议 1：添加已胡牌玩家信息

**方案 A：在特征中添加已胡牌标志**

```rust
// 扩展 GRP_SIZE 从 5 到 9
[kyoku, score[0]/10000, score[1]/10000, score[2]/10000, score[3]/10000,
 agari[0], agari[1], agari[2], agari[3]]  // 1.0 = 已胡牌, 0.0 = 未胡牌
```

**优点**：
- GRP 能知道当前已有几人胡牌
- 能准确预测"3人胡牌结束"的情况

**缺点**：
- 需要修改 `GRP_SIZE` 常量
- 需要重新训练 GRP 模型
- 需要修改特征提取逻辑

**实现难度**：🟡 中等

#### 方案 B：在特征中添加"剩余胡牌机会数"

```rust
// 扩展 GRP_SIZE 从 5 到 6
[kyoku, score[0]/10000, score[1]/10000, score[2]/10000, score[3]/10000,
 remaining_agari_count]  // 剩余可胡牌玩家数（4 - agari_count）
```

**优点**：
- 更简洁（只有 1 个额外维度）
- 直接表达"距离游戏结束还有多远"

**缺点**：
- 丢失了"哪些玩家已胡牌"的详细信息
- 仍然需要修改代码和重新训练

**实现难度**：🟡 中等

### 5.2 中优先级改进

#### 建议 2：添加定缺信息

**方案**：在特征中添加定缺状态

```rust
// 扩展 GRP_SIZE 从 5 到 9
[kyoku, score[0]/10000, score[1]/10000, score[2]/10000, score[3]/10000,
 ding_que[0], ding_que[1], ding_que[2], ding_que[3]]  // 定缺花色编码（0-2）
```

**优点**：
- GRP 能考虑定缺对排名的影响
- 能预测"花猪"情况

**缺点**：
- 定缺信息可能通过分数变化间接体现
- 改进效果可能不明显

**实现难度**：🟡 中等

### 5.3 低优先级改进

#### 建议 3：添加剩余牌数信息

**方案**：在特征中添加剩余牌数

```rust
// 扩展 GRP_SIZE 从 5 到 6
[kyoku, score[0]/10000, score[1]/10000, score[2]/10000, score[3]/10000,
 tiles_left/56.0]  // 归一化的剩余牌数
```

**优点**：
- GRP 能知道"距离流局还有多远"
- 可能有助于预测流局情况

**缺点**：
- 改进效果可能不明显
- 局数信息已经部分表达了时间信息

**实现难度**：🟢 低

## 8. 技术细节

### 8.1 修改 GRP_SIZE 的影响

如果修改 `GRP_SIZE`：

1. **需要修改的文件**：
   - `libblood/src/consts.rs` - 修改 `GRP_SIZE` 常量
   - `libblood/src/dataset/grp.rs` - 修改特征提取逻辑
   - `mortal/model.py` - 修改 GRP 模型输入维度

2. **需要重新训练**：
   - 所有现有的 GRP 模型都需要重新训练
   - 训练数据格式需要更新

3. **兼容性**：
   - 新模型与旧数据不兼容
   - 需要重新生成训练数据或进行数据迁移

### 8.2 特征提取实现示例

**添加已胡牌信息的实现**：

```rust
// libblood/src/dataset/grp.rs
// 在 StartKyoku 事件处理中
Event::StartKyoku { kyoku, scores, .. } => {
    // 获取当前已胡牌玩家（需要从事件序列中推断）
    let players_agari = infer_players_agari(events, kyoku);
    
    let mut kyoku_info = array_vec!([_; GRP_SIZE]);  // GRP_SIZE = 9
    kyoku_info.push(kyoku as f64);
    kyoku_info.extend(scores.iter().map(|&score| score as f64 / 10000.));
    kyoku_info.extend(players_agari.iter().map(|&agari| if agari { 1.0 } else { 0.0 }));
    
    game_info.insert(0, kyoku_info);
}
```

**挑战**：
- 需要从事件序列中推断已胡牌玩家
- 需要处理"3人胡牌结束"的情况
